#  Web Application & Penetration Testing
### CloudExify Cybersecurity Internship — Project 03

> **A controlled, authorized cybersecurity laboratory assessment of DVWA using Kali Linux, Burp Suite, Nmap, and supporting security tools.**

---

## Project Overview

This project demonstrates a practical **Web Application Security Assessment and Penetration Testing** workflow performed in a controlled Kali Linux laboratory environment.

The intentionally vulnerable **Damn Vulnerable Web Application (DVWA)** was used as the target so that common web-security weaknesses could be safely studied without targeting real-world systems.

The assessment covered:

- Laboratory environment preparation
- DVWA deployment and configuration
- Apache and MariaDB configuration
- Burp Suite proxy and HTTP traffic analysis
- SQL Injection testing
- Reflected Cross-Site Scripting (XSS) testing
- Cross-Site Request Forgery (CSRF) analysis
- Authentication / Brute Force observations
- File Upload testing
- Evidence collection and security documentation
- Risk and impact analysis
- Security recommendations

All testing was conducted only against the authorized, intentionally vulnerable laboratory application.

# Vulnerability Assessment

## 1. SQL Injection

### Finding
The DVWA SQL Injection module demonstrated unsafe handling of user-supplied database input.

### Evidence
A controlled test caused the application to return multiple database records instead of only the expected record.

### Risk
**High**

### Potential Impact
In a real application, SQL Injection may allow unauthorized database interaction, disclosure or modification of data, and potentially broader compromise depending on database privileges.

### Recommendation
- Use prepared statements / parameterized queries.
- Validate input on the server side.
- Apply least-privilege database permissions.
- Avoid direct concatenation of user input into SQL queries.

---

## 2. Cross-Site Scripting (XSS)

### Finding
Reflected XSS behavior was demonstrated in the controlled DVWA environment.

### Evidence
The submitted test input was reflected in the application response and JavaScript execution was observed.

### Risk
**Medium**

### Potential Impact
XSS can allow malicious client-side content to execute in a victim's browser and may affect application content or user sessions depending on the environment.

### Recommendation
- Apply context-aware output encoding.
- Validate and sanitize input.
- Implement a strong Content Security Policy (CSP).
- Avoid unsafe rendering of user-controlled data.

---

## 3. Cross-Site Request Forgery (CSRF)

### Finding
The DVWA password-change functionality was examined through Burp Suite to evaluate request protection.

### Evidence
The password-change request was captured and analyzed. A `user_token` parameter was present in the observed request.

### Assessment
The available evidence did **not conclusively demonstrate a complete unauthorized CSRF exploit**.

### Recommendation
- Use unique, unpredictable anti-CSRF tokens.
- Validate request origin where appropriate.
- Use suitable `SameSite` cookie settings.
- Protect all sensitive state-changing operations.

---

## 4. Authentication / Brute Force

### Finding
The DVWA authentication module was examined for authentication-security weaknesses.

### Evidence
Authentication requests and successful login behavior were observed within the controlled laboratory.

### Risk
**Medium to High**

### Potential Impact
Weak protection against repeated authentication attempts can increase the risk of password guessing and unauthorized account access.

### Recommendation
- Implement rate limiting.
- Add temporary delays or account lockout controls.
- Enforce strong passwords.
- Consider multi-factor authentication.
- Monitor repeated failed login attempts.

---

## 5. File Upload

### Finding
The DVWA file-upload functionality successfully accepted and stored a test `.txt` file.

### Risk
**Medium**

### Potential Impact
Insufficient file validation can become a serious risk if executable or otherwise dangerous file types are accepted in a production environment.

### Recommendation
- Use strict server-side file validation.
- Allow only required file types.
- Validate both extension and MIME type.
- Rename uploaded files.
- Store uploads outside executable web directories.
- Apply appropriate access controls.

# 🧠 Key Security Lessons

This project demonstrated several important principles of secure application development:

- Never trust user-controlled input.
- Use parameterized database queries.
- Encode output according to its context.
- Protect state-changing requests with strong CSRF defenses.
- Rate-limit authentication attempts.
- Apply secure session-management controls.
- Validate uploaded files on the server.
- Follow the principle of least privilege.
- Collect evidence before drawing security conclusions.
- Distinguish a demonstrated vulnerability from an inconclusive test.

---

# 🛡️ Recommended Security Controls

A secure web application should combine:

- Input validation
- Output encoding
- Parameterized SQL queries
- Secure authentication
- Rate limiting
- Strong session management
- HTTPS
- Secure and HttpOnly cookies
- CSRF protection
- Content Security Policy
- Strict file-upload validation
- Least-privilege access
- Continuous vulnerability assessment
- Regular security testing and retesting
